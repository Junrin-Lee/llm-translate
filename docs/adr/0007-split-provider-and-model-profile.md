# Split the flat Provider Profile into an LLM Provider and a Model Profile

**English** · [简体中文](./0007-split-provider-and-model-profile.zh-CN.md)

Through v0.3.0 a single `ProviderProfile` record held three unrelated things at once: a connection (protocol, Base URL, API Key), a model choice, and that model's parameters. Users who wanted two models behind one OpenAI-compatible gateway therefore had to create two full profiles and retype the same Base URL and API Key, and rotating that key meant editing every copy of it. Storage is now two records — `LlmProvider` for the connection and `ModelProfile` for one model on one provider — and `defaults.global` plus the per-feature overrides point at a `ModelProfile.id`. The runtime shape does not split: `resolveProfileFrom()` joins a provider with a model into a flat `ResolvedProfile` (the old `ProviderProfile`, renamed), so the two hand-rolled adapters from ADR-0003 keep the exact input they have today. We rejected the cheaper "duplicate this profile" button: it removes the retyping but not the key rotation, and the profile count keeps multiplying as translation features are added. We also rejected letting the v1 → v2 migration merge providers on its own, for the reason below.

## Consequences

- `defaults.*` binds to `ModelProfile.id`, never to a provider id. Pointing routing at the connection instead would make it impossible to give Selection Translation a cheap model and Page Translation a strong one on the same gateway, which is the whole reason for the split.
- The split is storage-only. `src/llm/` sees one flat `ResolvedProfile` and stays unaware that two records produced it, so the protocol adapters, their retry wrapper, and their tests carry no new concepts.
- The v1 → v2 migration is a lossless 1:1 expansion with **no dedupe at all**: every flat profile becomes one provider plus one model, even when several profiles are byte-identical on protocol, Base URL and API Key. Merging automatically would risk collapsing two accounts that happen to share an endpoint into one credential, which silently bills and rate-limits the wrong key. Convergence is instead offered in the settings page as an explicit action, keyed on all three fields matching exactly, so the user confirms it.
- The migrated `ModelProfile` keeps the v1 profile's `id`. Every id already stored in `defaults` therefore stays valid and the migration never touches routing.
- `temperature`, `maxTokens` and `timeoutMs` live on `ModelProfile`. `LlmProvider.timeoutMs` is only a connection-level default that a model's own value overrides. Hoisting the parameters onto the provider would stop two models on one connection from having different temperatures, recreating the original complaint one layer up.
- Connection health and model health are separate probes: `test-provider` calls the models endpoint and judges auth plus reachability, `test-model` sends one `max_tokens: 1` completion. A single combined test lets "the model name is wrong" and "the key is dead" impersonate each other, so the error points at the wrong field.
- `listModels` no longer swallows its errors. Returning `[]` for an auth failure made the settings page say "no models returned, enter the model name manually", which walks the user away from the actual problem. An empty array now means only that the endpoint has no models; everything else throws. `list-models` reports a failure as an `error` event because the user wanted a list and did not get one, while `test-provider` reports the same failure as `test-result` with `ok: false` because "no" is a valid answer to the question it was asked.
- Deleting an `LlmProvider` is blocked while any `ModelProfile` still references it, rather than cascading. Cascading would let one click on a connection destroy a batch of model configurations the user spent time on.
- On import, a `ModelProfile` whose `providerId` is absent from the same file is rejected with a message naming the offending model. Accepting an orphan silently defers the failure to the next translation, by which point none of the context that would explain it is still available.
- ADR-0004's rule about `name` still holds, now per type. See the amendment recorded there.
